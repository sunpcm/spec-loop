# 需求与验收

文档日期：2026-11-14。状态：开发设计草案，待实施。

## 1. 目标与范围

搭建一个单机运行、真实连接 GitHub 的 MVP，演示以下链路：

1. 修改需求文档 → 提交并推送到 `main` → Planner 同步 Issue → Worker 编码、校验并提 PR。
2. 前端发生错误 → 接收并去重 → Triage 判断契约缺失或实现缺陷 → 文档 PR 或修复任务 → 重新进入开发链路。
3. 用户在 GitHub 人工 Merge → 守护进程识别 → 构建并切换本地预览 → 发布部署回执。

系统只自动创建和更新任务、分支、提交、PR，以及部署已经人工合并的代码。任何角色均不得自动 Merge，也不执行远程服务器部署。

MVP 默认：单个 GitHub 仓库、单个本地守护进程、一个产品示例、一个需求块对应一个主 Issue、全局同时运行一个 Pi 作业。复杂需求继续在文档内拆成多个独立需求块，不让模型自行拆出无法追溯的新需求。

## 2. 事实来源与生效时机

| 对象 | 权威范围 | 生效条件 |
| --- | --- | --- |
| `docs/specs/*.md` | 前端应该具备的功能、异常边界及验收行为 | 文档已经进入 GitHub `origin/main` |
| GitHub Issue | 当前任务状态、对应需求版本、执行失败与恢复记录 | GitHub 写入并回读确认 |
| GitHub PR | 待合并的代码或需求补丁、验证证据 | 用户人工 Merge 后进入主线 |
| 本地状态文件 | 游标、锁、重试、错误队列、部署位置 | 仅是运行缓存，不覆盖文档或 GitHub 事实 |
| `docs/development/` | 编排系统的工程契约与维护说明 | 开发者维护，不参与需求扫描 |

未提交的文件保存不产生 Issue。只在本地提交但没有推送的文档也不产生远端任务；守护进程可以在安全的快进条件下帮助推送，具体见架构文档。Triage 的未合并文档 PR 不改变现行需求。

“所有状态真实同步 GitHub”指任务、PR、失败、部署结果等业务状态。进程 PID、锁、原始错误堆栈等本机细节不上传，也不应提交凭据或运行缓存。

## 3. 需求文档契约

### 3.1 文件与锚点

- MVP 只扫描 `docs/specs/` 目录直接包含的 `.md` 文件，不递归扫描子目录。
- 每个需求块必须以 `### [REQ-XXX-01] 需求标题` 开始。
- ID 采用 `REQ-[A-Z0-9]+-[0-9]{2,}`，如 `REQ-CNT-01`；同一仓库中全局唯一、稳定，不因标题改名或文件移动而改变。
- 需求块到下一个合法三级需求标题或文件结尾为止。块内分节使用四级及更低标题。
- Markdown 围栏代码块中的示例锚点不参与解析；重复 ID、空标题、非法需求标题或非法文本结构阻断本轮整个需求快照。
- 具有约束力的功能、边界和验收内容必须写在需求块内。文件前言只用于导航，不隐式提供影响多个需求的共同规则。
- 块哈希覆盖标题和正文；统一换行符后计算，不做会掩盖文字变更的语义归一化。单纯路径移动且内容不变时只更新来源路径。
- ID 不复用于其他功能。显式更换 ID 按删除旧需求、创建新需求处理。

### 3.2 初始计数器示例

实施时创建 `docs/specs/counter.md`，初始内容建议如下。本节是设计示例，当前不创建可触发任务的正式需求文件。

```markdown
# 计数器演示

### [REQ-CNT-01] 计数器与自定义步长

#### 功能
- 页面展示计数值，初始值为 0。
- 输入合法整数步长后，点击“增加”按该步长累计。
- 点击“重置”将计数值恢复为 0。

#### 验收
- 初始显示 0；步长 2 时点击一次显示 2。
- 重置后显示 0，原步长保留。
```

初版故意没有规定空步长、非数字和超范围输入的用户行为。演示代码对非法输入显式抛出可识别错误，例如 `CounterInputError: step is empty`，由错误边界展示恢复入口并上报。不能依赖 `Number('')` 或 `NaN` 自动产生异常，因为这两者本身不会抛错。

“故意可报错”是演示夹具，不作为 Worker 可保留错误的长期需求。初始构建与合法路径测试必须通过；错误场景作为可复现演示用例单独记录。

建议的文档补丁候选：空输入时禁用增加按钮并显示“请输入整数步长”；无效输入不改变已有计数值。Triage 可以将该候选做成 `spec-patch` PR，只有人工合并后才成为有效契约。

## 4. 闭环 A：文档变更驱动开发

### 4.1 触发与对账

监听器以文件与 Git 引用变化作为唤醒信号，周期性轮询作为兜底。实际输入是“上次成功对账的远端提交”与“本次捕获的 `origin/main`”的需求快照及 `git diff`，不能只比较工作区文件或 `HEAD~1`。

首次启动时，以远端当前有效需求与全部受管 Issue 对账，补建缺失任务。重启后补偿停机期间的提交、合并和任务更新。

| 需求变化 | 必须执行的行为 |
| --- | --- |
| 新增 ID | 创建主 Issue，标签 `pi-task`、`status:todo`，记录文档路径、需求哈希和提交 SHA |
| 修改已有 ID | 更新原主 Issue 的受管内容；必要时重新打开；作废旧版本作业和 PR；回到 `status:todo` |
| 删除 ID | 关闭对应受管 Issue，说明需求已删除；停止未发布作业，作废未合并 PR |
| 内容不变 | 不重复建单，不重复运行 Worker，不重复评论 |
| 同一 ID 仅移动文件 | 保留 Issue 关联，只更新来源位置 |

对修改或删除关联的旧 PR，必须留下原因和新旧版本信息；建议同时关闭尚未合并的旧 PR，并移除其关闭 Issue 的关键字，防止误合并旧版本。保留历史，不自动删除远端分支。

只查 Open Issues 无法复用已关闭任务，也无法处理 GitHub 自动关单后的部署。Open 列表用于待办发现，完整映射必须同时包含受管 Closed Issues 和已记录的 PR。

### 4.2 Worker

1. 抢占 Issue 与需求锁，确认当前需求版本，更新为 `status:processing`。
2. 从捕获的远端提交创建独立 worktree 和 `pi/req-...` 分支。
3. Worker Pi 读取对应需求及必要上下文，只能修改 `src/` 下允许的前端源文件和行为测试。
4. 通过受控命令运行类型检查、行为测试和生产构建。
5. 控制器验证修改路径、基线和需求版本仍有效，再提交、push、创建 PR。
6. PR Body 包含 `Closes #<issue_number>`、需求 ID、需求哈希、来源 SHA、验证结果。创建成功并回读后更新 `status:in-review`。
7. 失败时置 `status:failed` 并评论错误摘要，不能无限重新调度。

若当前主线已经完整满足该需求，允许返回 `already-satisfied`，避免为了提 PR 制造无意义修改。这是建议增加的幂等分支：必须有独立固定验收及构建证据，并确认同一 SHA 的本地部署可用，才直接回执并标 done；无法证明就保留任务待处理，不能凭模型自报关单。正常新增行为仍必须走代码 PR 和人工 Merge。

分支示例：`pi/req-cnt-01-i12-r<hash8>`。需求修订或修复子任务使用独立分支，避免重复使用已经 Merge 的分支。

## 5. 闭环 B：错误驱动契约或实现修复

### 5.1 错误入口

提供仅监听回环地址的 HTTP 服务，默认端口 `4000`，接收 `POST /api/error-report`。

原生 TypeScript 前端提供统一错误边界包装器，并监听 `window.error` 和 `unhandledrejection`。若后续改用 React，React ErrorBoundary 仍需配合这两个监听器，事件处理和异步错误不能只依赖组件边界捕获。

上报至少带有错误类型、消息、堆栈、页面、应用版本、可选需求 ID、前端生成的报告 ID。错误面板显示上报是否成功，提供恢复操作；上报失败不得再次抛错形成递归上报。

### 5.2 Triage 决策

| 分类 | 判断条件 | 产出 |
| --- | --- | --- |
| `spec-gap` | 复现证据明确，现行需求没有定义该边界 | 仅修改对应需求块的 `spec-patch` PR，说明补充理由；等待人工 Merge |
| `implementation-gap` | 能引用现行需求中的明确条款，代码行为违反该条款 | 与主 Issue 关联的修复任务，标签 `pi-task`、`status:todo`；不改文档 |
| `needs-human` | 无法定位、无法复现、需求含糊或涉及较大产品取舍 | GitHub 分诊记录，`status:failed`，等待用户澄清；不触发 Worker |
| `stale-release` | 错误来自已经被替换的部署版本 | 关联现有部署或修复记录，提示刷新，不产生重复修复 |

“修复子 Issue”在 MVP 中指正文包含 `Parent issue: #N` 与受管父子标识的普通 Issue，不依赖 GitHub 原生子 Issue API；需要原生树形层级可以后续扩展。

文档补丁 PR Merge 后，变化即使由机器人生成，也必须进入闭环 A。文档已规定的错误不应为了制造“文档驱动”效果再改文档。

### 5.3 去重与循环上限

- 同一部署版本内，以需求 ID、错误类型、规范化消息、稳定栈帧生成指纹。
- 去掉堆栈中的行列号和构建资源哈希等不稳定片段；不同部署保留独立关联，防止永久去重吞掉回归。
- 错误写入本地持久队列成功后才返回接受；同指纹在默认 10 分钟内合并计数。
- 同一需求版本与错误指纹最多维持一个活动分诊、一个活动文档补丁或修复任务。
- 每个任务默认最多 2 次执行尝试；同一错误关联的自动需求修订链最多 2 轮。超过后在 GitHub 留记录并停在人工处理。
- 指纹跨部署另有稳定的“错误族”键，修订链预算跨新构建继承；不能通过每次修改 SHA 重置预算。

## 6. 闭环 C：人工合并与部署

守护进程按记录的 PR ID 轮询真实合并状态，同时发现停机期间合并的受管 PR；不能只扫描 Open Issues，也不能仅凭 `pi/` 分支名前缀决定部署。

| 合并结果 | 处理方式 |
| --- | --- |
| `pi/req-*` 代码 PR 合并到 `main` | 捕获远端主线 SHA，在部署 worktree 构建，健康检查后切换预览 |
| `pi/spec-*` 文档补丁 PR 合并到 `main` | 触发需求对账，不把文档补丁当作代码修复部署成功 |
| PR 被关闭但未 Merge | 记录人工拒绝，不部署，不自动重新创建相同 PR |
| 旧需求版本 PR 被误合并 | 记录版本失配，保持最新需求待办，不能标最新版本完成 |
| 部署失败 | 保持旧预览；Issue 为 `status:failed`，错误评论；只重试部署，不重新编码 |

必须正视 GitHub 行为：当 PR Body 包含 `Closes #N` 且合并进入默认分支时，GitHub 会先自动关闭 Issue。因此，保留用户要求的 `Closes` 时，**Issue 的 Open/Closed 不能单独表示部署完成**。完成标准为 `status:done` 加包含部署 SHA 的成功回执。部署失败时重新打开 Issue，但其恢复动作必须标为 `deploy-only`。

部署成功后控制器更新 `status:done`，确认 Issue 关闭，并发布包含构建结果、服务地址、部署 SHA、耗时和日志摘要的回执。修复子任务只关闭自己；只有主任务当前版本也满足完成条件时才改变主任务状态。

## 7. 明确不纳入 MVP 的内容

- 多机器调度、多实例竞选、GitHub Actions 云端执行、自动 Merge、真实生产部署。
- Agent 自行修改依赖、构建工具、编排代码、权限配置或测试脚本来获得通过。
- 自动解决复杂跨需求依赖、PR 冲突或仓库历史重写。
- 删除需求后自动推断如何移除既有产品功能。MVP 只完成用户要求的关单和旧作业撤销；要移除既有行为，应显式新增可验收的退役需求。
- 零配置模型认证。`pi --version` 通过不代表模型可调用，必须单独做真实 Pi 冒烟检查。

## 8. 完成标准

| 编号 | 验收场景 | 成功判据 |
| --- | --- | --- |
| AC-01 | 初始检查 | Git、远程仓库、默认分支、gh 登录、Pi 版本/能力/模型、隔离探针均通过；标签幂等创建 |
| AC-02 | 新增需求 | 真 GitHub 上只产生一个正确主 Issue，之后产生通过校验的代码 PR |
| AC-03 | 修改需求 | 复用原 Issue，旧 PR 留痕作废；旧进程不能发布过期代码 |
| AC-04 | 删除需求 | 对应任务关闭、旧作业取消；解析失败绝不批量关单 |
| AC-05 | 文档缺边界 | 同一错误重复上报只产生一份活动文档 PR，且 PR 仅改 `docs/specs/` |
| AC-06 | 文档补丁 Merge | 自动触发 A，Worker 修复代码；文档机器人提交不被误过滤 |
| AC-07 | 代码违约 | 直接生成修复子任务，Worker PR 仅改 `src/` |
| AC-08 | 人工 Merge | 自动部署准确的远端主线版本，健康检查成功后标 done、评论、关单 |
| AC-09 | 故障 | Pi 超时、构建失败、gh 失败和部署失败均有可恢复状态与错误证据 |
| AC-10 | 并发与重启 | 双击启动被拒绝；同需求互斥；进程重启不重复建单、提 PR 或评论 |
| AC-11 | 权限隔离 | Worker 越权写 docs、Planner 写 src、路径穿越和 symlink 探针均被执行层阻断 |
| AC-12 | 可观测性 | 终端出现规定阶段前缀，日志可关联 REQ、Issue、PR、SHA 和作业 |

真实闭环验收必须保存 GitHub Issue/PR URL、需求版本、代码 SHA、本地部署 SHA 和操作日志。模拟 gh/Pi 的自动化测试只能证明状态机与错误处理，不能替代真实 GitHub + Pi + 浏览器演示。
