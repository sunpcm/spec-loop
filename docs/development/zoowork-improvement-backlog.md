# ZooWork 借鉴项与 Spec Loop 改进清单

日期：2026-11-15。状态：候选改进清单，全部未启动；本轮只整理，不开发。

Spec Loop 应优先强化需求到发布的可信交付。ZooWork 值得借鉴的是明确交付标准、保存执行过程、单独评价结果，以及让人工审批获得足够证据。跨行业 Builder、模型训练和通用云端 Agent 平台暂不进入当前范围。

## 当前基础与主要缺口

基线为本地 `main` 的 `5a4bdf6`。相对本地 `origin/main` 引用领先 5 个提交；本次未刷新远端，也未核验运行中控制器版本。以下区分源码能力与真实启用状态。

| 已有基础 | 改进应落在哪里 |
| --- | --- |
| 文档 PR 与代码 PR 两次确认；受控入口绑定身份、会话、SHA 和有效期 | 补齐当前版本的真实验收与审查证据，不重做审批引擎 |
| Worker 限制 `src/**`，运行固定类型检查、测试、构建，随后重新检查需求版本 | 补需求行为覆盖和独立 CI，不用测试数量替代需求覆盖 |
| 持久状态、操作记录、尝试次数及分阶段恢复已有实现 | 统一关联和可导出的交付记录，逐步补事件历史，不另建第二套调度状态 |
| 部署检查 SHA、候选首页和静态资源，再切换预览 | 补真实入口的浏览器行为验收，单列本地与云端结果 |
| 独立本机面板已有真实只读模式和合成演示 | 展示真实证据、等待原因和下一责任方；保持只读边界 |

可直接确认的缺口：`tests/frontend.test.ts` 主要覆盖步长解析、增加、入口契约和构建版本；当前 `tests/` 未找到减少、翻倍及相应按钮交互的直接测试。仓库未见 `.github/` 工作流。源码中减少、翻倍已有实现，不能把实现存在等同于行为验收通过。

## P0 先补交付保障

### ZW-01 需求验收项与行为证据对应

借鉴 ZooWork 单独定义结果好坏的做法，把现有需求的每条验收对应到行为测试、人工观察及证据位置。先用派生清单给验收项稳定编号，绑定需求哈希；无需立即改写需求文档格式或新增规格 DSL。

- 首批覆盖初始值、增加后减少、翻倍、翻倍后重置，以及步长在各操作后保留的完整序列；补非法输入和溢出边界。
- 区分函数测试与浏览器按钮接线测试。行为探针放在 Worker 无权修改的受控测试范围内。
- 以故意断开翻倍点击处理器、改错减少方向或让重置清空步长等负例验证探针确实能发现问题；这类验证用于交付行为和权限，不给低影响文档修改新增测试负担。
- 完成标准：当前六条验收各有结果与证据；未覆盖项明确为未验证；负例可使对应检查失败，恢复后重新通过。

### ZW-02 仓库独立 CI

把质量检查从单机调用扩展为对 PR 对应版本可回读的独立证据。此项是 Spec Loop 的配套保障，不代表 ZooWork 已替我们提供 GitHub CI。

- Node 24 下运行 `npm ci`、`npm run typecheck`、`npm test`、`npm run build`、`npm run build:panel`，再纳入 ZW-01 的行为验收。
- 当前测试存在通过 `SPEC_LOOP_VERIFY=1` 启用的本机 HTTP 集成，必须在适配环境中运行并记录 skip；Linux CI 通过不能代替 macOS `sandbox-exec` 的真实隔离验证。
- 模拟测试与构建不获得模型或 GitHub 凭据；凭据与外部真实调用继续留在受控验收环节。
- 完成标准：故意引入行为错误能使对应 PR 检查失败；修复后通过；证据绑定检查的提交。required checks 和分支保护另行确定，避免直接改变当前合并策略或误阻断 docs-only PR。

### ZW-03 当前版本真实链路验收与文档状态对齐

用 ZooWork 按真实工作流验收的思路，复核现有单仓链路。历史真实验收继续有效于其对应版本，不代表后来新增的受控入口和面板已全部启用。

- 先核对文档所述版本、源码版本、控制器运行版本、实际本地发布和云端发布；修正“本分支新增”“待启用”等易过时表述，保留历史版本与证据。
- 走通一条经用户同意的现有范围需求：飞书接收、文档 PR、人工确认、代码 PR、人工确认、本地发布与真实入口行为验收。云端发布单独核对 SHA 和结果。
- 基于现有能力验证重复消息、重启、主线漂移、检查失败、部署失败、通知失败，以及合并结果未知后的只读对账；不得为验收扩大到 Triage、自愈或自动 Merge。
- 完成标准：每个场景有实际输入、版本、产物、结果和恢复证据；重复消息不重复生成产物，未知合并结果不重发写请求，失败发布不覆盖稳定预览，重试只恢复未完成阶段。外部受限项保留未验证状态。

## P1 提升证据与复用

### ZW-04 统一交付记录与独立结果评价

借鉴 trajectory 与 outcome 的分离。复用现有 request、job、attempt、PR 和部署记录，形成可导出的交付记录，不引入新的权威状态库。

最小信息包括需求 ID 与哈希、来源主线 SHA、文档与代码 PR、Worker head SHA、合并 SHA、各发布目标 SHA、检查命令与结果、证据引用和评价版本。执行状态、健康状态、行为验收和人工接受分别记录，缺失项为未知。原始输出、个人标识和确认码不直接进入导出。

完成标准：单条记录可回答“按哪版需求、交付了哪版代码、在哪里验证、谁以什么标准接受”；执行成功但行为错误时，两类状态可以同时正确表达，不能自动把已部署标成需求已验收。

### ZW-05 结构化阶段事件与真实面板证据

借鉴持久事件历史，按作业关联阶段开始、结束、等待人工、失败、恢复和部署回执。采用有界事件存储、序号、时间、作业关联和脱敏规则；先提供控制器实际知道的阶段，不伪造模型内部步骤。

现有持久状态仍负责调度与恢复，事件服务于观察和回溯。必须处理重复、断线续读和快照对齐；观察面板或事件展示失败不得中断 GitHub 主链路。事件读取、面板回放不能调用任何业务写动作。

完成标准：面板重连后保持同一作业的尝试历史，可定位卡在哪一步、由谁处理、依据是什么；控制器离线、未知和真实失败显示不同状态；只读服务边界保持有效。

### ZW-06 改善人工审查所需的预检摘要

借鉴关键操作前提供清晰审查上下文的方式，在现有飞书预检中按文档 PR 与代码 PR 展示变更摘要、需求差异、相关验收、文件范围、检查证据、目标版本和失败或缺失项。首版普通消息加链接即可，不先做复杂交互卡片。

SHA、身份、会话、TTL、单次许可和确认前重检已有实现，应复用并补验收。面板当前仍只读，本项不使其确认或重试按钮连接真实业务。

完成标准：操作者在确认前能判断改了什么、验证了什么、仍缺什么；head 或基线变化后旧许可失效，内容再清晰也不能替代授权校验。

### ZW-07 版本化角色 SOP 与完成标准

借鉴 Skills 复用专业方法的方式，把现有 spec-author、Planner、Worker 的固定 Prompt、输入、输出格式、完成标准和失败处理约定按角色管理，并在交付记录中保留版本或哈希。角色和数量保持当前范围。

Skills 是指令，不授予工具权限。继续禁用任意资源发现；只有受信、固定版本的角色材料进入作业。成功经验先经人工和独立评审整理为变更，不自动修改权威规格、权限或角色规则。

完成标准：同一任务可以追溯使用的 SOP 版本；切换版本经过受控验证；SOP 中的越权要求无法突破执行层边界。

### ZW-08 有效交付的质量耗时与成本指标

借鉴按业务结果衡量 Agent 的方式，先统计少量真实任务：验收通过数与总数、首次通过率、人工实际处理时间、等待时间、运行时间、失败恢复时间和尝试次数。

成本包括失败与重试的消耗。使用实际请求的 provider/model、可获得的 token/usage 和带日期价格；缺失时记未知，估算与账单分开，不根据路由名称断言底层模型身份。小样本展示数量与逐项分布，不用无依据的百分比、P95 或“节省额度”结论。

完成标准：对一组固定需求，能同时说明交付质量、人工负担和总消耗；比较模型或运行时前固定任务、验收标准和预算。

## P2 按需求触发扩展

### ZW-09 可替换运行时与能力验证

借鉴托管运行时把执行生命周期与应用分开的方式，沿现有 Pi runner 边界评估适配接口，覆盖启动、事件、取消、完成、超时、产物与错误分类。先有第二种实际运行时需求，再验证抽象；不为可扩展性先做插件市场或动态加载器。

Git、需求版本、审批与发布权限继续由控制器掌握。每种适配单独证明隔离、凭据不外泄、取消后停止写入和输出校验；回合结束事件不等于进程退出或作业交付完成。

完成标准：相同受控任务在候选运行时通过同一套能力与越权探针，切换不重复已有外部副作用；缺能力时明确拒绝，不能静默降低隔离。

### ZW-10 只读需求一致性检查与来源索引

借鉴企业知识和执行结果沉淀，先建立需求、代码、验收、发布之间可检索的来源引用，区分已规定、已实现、已验证和已发布。索引是可重建派生物，不能覆盖 Git 中的权威需求。

完成标准：回答“此功能依据是什么、当前发布是否验证”时能给出路径、哈希、SHA 和证据；过期或缺证据明确提示。语义检查仅报告其覆盖范围内的疑点，不自动改文档或宣称完整证明一致性。

### ZW-11 单机运维与状态恢复保障

借鉴托管平台对运行生命周期的重视，先解决单机责任边界：启动诊断、进程恢复、磁盘和日志预算、状态与发布证据的加密异机副本及恢复演练。面板健康、控制器在线和静态站可访问分开检查。

当前串行写与 rename 不足以证明断电持久性；需要先定义故障范围，再决定 fsync、备份或存储升级。状态可能包含确认码和身份信息，备份和导出采用不同权限与脱敏规则，恢复时旧许可不得重新获得写权限。

完成标准：在隔离环境从备份恢复后能解释当前阶段、核对远端已有产物，并拒绝过期许可；控制器停止时不会把静态站在线当成工作流可用。长期无人值守或迁移前，本项升为前置工作；具体选址另行核验资源与故障域，不默认云迁移。

### ZW-12 第二个真实仓库试点

借鉴按场景试点再推广的方法，在 P0 验收完成后选一个小型真实仓库，明确只允许的需求与源码路径，重新验证权限、构建、检查和部署契约。

完成标准：第二仓库按同一套需求和交付记录完成真实交付，暴露并记录通用部分与项目特有部分；不靠继续增加计数器演示节点证明通用化。

## 建议启动顺序与暂缓项

下一轮仅考虑 ZW-01、ZW-02、ZW-03：先明确验收与基线，可并行补行为检查和 CI，再对当前版本做真实链路验收。之后用 ZW-04、ZW-07 形成交付记录与角色约定，逐步推进 ZW-05、ZW-06、ZW-08。P2 按各自触发条件单独立项。

继续暂缓跨行业 Agent Builder、拖拽流程编辑器、插件市场、多 Agent 并发、多租户、通用自动学习或模型训练、Triage 与错误自愈。ZooWork 的公共文档明确通用 outcome 标签与后训练流程仍由应用负责，不能把其营销中的持续优化理解成可直接移植的全自动能力。

本清单不改变 `docs/specs/*.md`、现有运行权限或当前开发范围；进入实施时再拆分指定 worktree 的实施任务，由主 Agent 独立评审、检查并集成，真实 Merge 按既有用户确认流程执行。
