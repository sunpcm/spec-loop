# ZooWork 与 Spec Loop 对比分析汇报

日期：2026年11月15日

本报告用于项目定位和后续改进讨论。ZooWork 按公开产品与技术文档分析，Spec Loop 按当前项目文档和本地源码分析；对比结论不构成开发启动或平台采购决定。

## 一 核心结论

**ZooWork 值得我们学习的，是把 Agent 从一次调用组织成可持续交付的产品：明确专业角色与完成标准，承载执行过程，让人参与关键决策，再根据结果改进工作方法。**

从公开产品设计看，ZooWork 覆盖专业 Agent 构建、托管运行和企业实施，面向的场景比当前 Spec Loop 更广。Spec Loop 则聚焦需求文档到软件发布，已经建立需求版本、受限执行、两次人工确认和发布检查等控制机制，当前仍以单仓库、本机计数器 Demo 验证。

我们的优先方向应是把现有交付链路做可信、做可复查，再逐步降低使用和维护成本。下一轮最值得投入的是三件事：**补齐需求行为验收、建立独立 CI、完成当前版本真实链路及失败恢复验收。** 随后再建设统一交付记录、真实阶段事件、角色 SOP 和交付指标。

## 二 双方定位与共同方向

ZooWork 将自己定位为面向领域专家和前线部署工程师的 Agent 交付平台，提供 Agent Builder、Managed Agent API 和企业方案。其核心目标是让专业工作方法进入可运行的 Agent。[产品定位](https://zoowork.ai/zh)

Spec Loop 的目标是让已确认的需求进入受控开发流程，并通过检查、审查和发布证据完成软件交付。需求文档是当前前端产品行为的权威来源，Issue 和 PR 记录执行过程。[项目定位](../../README.md)

| 对比维度 | ZooWork 的公开产品设计 | Spec Loop 当前方向 |
| --- | --- | --- |
| 面向用户 | 领域专家、开发者和企业业务团队 | 当前单操作者，围绕软件需求与交付 |
| 输入依据 | 专业知识、角色指令和工作方法 | 已审查并进入主线的需求契约 |
| 交付目标 | 完成不同岗位的专业任务 | 交付满足对应版本需求的软件变更 |
| 执行组织 | 可复用 Agent 与托管运行 | 本机控制器与受限 Pi 角色 |
| 人工参与 | 对关键工具操作审批 | 分别确认文档 PR 与代码 PR |
| 可观察性 | 持久会话和执行事件 | 阶段状态、尝试记录、PR 与部署记录，以及本机只读面板 |
| 改进基础 | 执行记录与结果反馈 | 当前主要依靠检查、评审和具体交付证据，统一评价尚待建设 |

双方都在解决“如何把人的意图转为受控成果”。相似的规划、工具调用和审批机制说明方向有交集；产品覆盖范围与软件交付约束的侧重点不同，不能仅按功能数量判断优劣。

## 三 ZooWork 的优势与我们的学习方向

### 1 围绕工作结果组织产品价值

ZooWork 的企业方案把真实工作流试点、联合实施和业务指标验收放在同一条落地路径中。[企业方案](https://zoowork.ai/zh/enterprise)

这一设计的优势，是让使用者更容易回答三个问题：Agent 负责什么工作、交付是否达标、是否值得继续投入。对我们而言，“自动生成了代码 PR”只说明流程推进了；用户更关心需求是否实现、发布是否可用，以及自己需要花多少时间介入。

**我们要学习：用交付结果表达项目价值。** 对外说明从“接了什么模型、画了多少节点”转向“完成了哪些需求、如何验证、失败怎样恢复”。量化收益以真实任务记录为依据。

### 2 把专业方法沉淀为可复用资产

ZooWork 用 Skills 承载任务方法，并明确指令与工具权限是不同层次。[Skills 文档](https://zoowork.ai/docs/zh/build/skills)

这为持续复用和迭代工作方法提供了结构。我们已有 spec-author、Planner 和 Worker 的角色约定，可以沿现有边界，把输入、输出、检查标准、失败处理和版本一起管理。这样出现问题时，能够追溯当时采用的工作方法，也便于比较一次规则调整是否有效。

**我们要学习：让成功经验形成经过评审的角色 SOP。** 规则变更继续受控，不自动改写权威需求，也不因加载一份指令就增加执行权限。

### 3 将运行生命周期作为平台能力

ZooWork 的托管架构分别管理会话与文件状态、执行事件和沙箱计算生命周期，支持等待后继续工作。[架构文档](https://zoowork.ai/docs/zh/get-started/architecture)

这一分层有助于应用减少对长驻进程和即时连接的依赖。我们目前的控制器、Pi 与飞书连接依赖本机；电脑停止运行时，静态页面可以继续访问，需求处理却会停止。后续应清楚定义启动、停止、超时、取消和恢复的含义，再决定是否引入其他运行时或迁移部署。

**我们要学习：先建立清晰的生命周期契约与恢复能力。** 云端托管是可选实现方式；当前没有必要仅为形式相似就复制其基础设施规模。

### 4 把人工审批嵌入可执行的工作流

ZooWork 支持工具执行前暂停审批，同时明确应用仍须负责实际业务授权。[权限策略](https://zoowork.ai/docs/zh/build/permissions)

这一设计可让人机协作发生在具体操作发生之前。Spec Loop 已有身份、会话、SHA、有效期和确认前重检等控制机制，下一步应提升审查信息质量：让操作者知道改了什么、依据哪版需求、哪些检查已通过、还有什么未验证。

**我们要学习：让确认建立在可检查的证据上。** 首先改善现有飞书预检摘要和链接，不必先增加复杂卡片或把只读面板改为操作台。

### 5 区分执行过程与交付质量

ZooWork 将执行轨迹与独立的结果评价分开，并指出正常结束不代表答案正确或有用。[Agent 轨迹文档](https://zoowork.ai/docs/zh/get-started/trajectories)

这是最值得我们直接吸收的设计。Spec Loop 当前已有需求、作业、尝试、PR 和部署信息，但还需要把它们组织成一条可复查的交付记录，并分别表达“检查通过、部署健康、需求验收、人工接受”等结果。

**我们要学习：用证据连接全过程，用标准评价最终结果。** 例如页面版本正确且静态资源可访问，仍不能单独证明翻倍按钮满足需求。发生失败时，也应保留原尝试及后续恢复记录，避免最终成功覆盖中间事实。

### 6 用试点和反馈决定是否扩展

ZooWork 企业方案将试点后的扩展、迭代或停止交给业务价值验收。[企业实施路径](https://zoowork.ai/zh/enterprise)

这种方式比先铺开平台功能，更容易约束投入并发现真正瓶颈。我们当前只有计数器 Demo，继续增加演示节点无法充分验证通用性。应先形成一个可信的真实成功样本和关键失败恢复样本，再选择第二个小型仓库验证哪些部分可以复用。

**我们要学习：按场景验证价值，再决定扩大范围。** 第二仓库试点的目标是暴露项目差异与维护成本，不能预先把它作为通用能力已成立的证明。

## 四 我们已有的基础与需要补齐的差距

### 应保留的项目基础

- **版本化需求契约。** 聊天表达意图，经过审查的主线文档定义当前产品行为；实现和发布必须对应版本。
- **控制器掌握外部执行权。** Agent 输出候选计划或文件内容，由控制器检查路径、版本和结果后执行 Git 等操作。
- **分阶段人工确认。** 文档与代码分别确认，权限不能由模型自行扩大。
- **明确完成证据。** 构建、健康检查与发布回执分别记录，本地结果与云端结果分开核对。

这些基础构成当前软件交付场景的明确设计方向，但还需要更多真实交付样本证明效果，也不能据此断言其他平台没有类似能力。

### 当前最明显的差距

| 差距 | 当前表现 | 对项目的影响 |
| --- | --- | --- |
| 需求行为覆盖不足 | 减少、翻倍及其与重置、步长的组合行为缺少直接测试覆盖 | 代码和构建通过后仍可能遗漏用户可见的问题 |
| 独立验证尚缺 | 当前本地仓库未见 CI 工作流 | 检查证据主要依赖本机流程，PR 缺少统一的独立复验入口 |
| 当前能力与运行状态需要对齐 | 新旧文档对启用状态存在不同表述 | 容易混淆代码已存在、控制器已加载和真实验收已通过 |
| 交付证据尚未统一 | 状态、PR、日志和发布信息分散 | 审查、复盘与模型比较需要额外人工整理 |
| 运行保障仍受单机限制 | 控制器与飞书连接运行在本机 | 可用性依赖本机，需要恢复、备份及运维边界 |
| 通用化缺少真实样本 | 当前围绕计数器验证 | 不能直接推断第二仓库的适配成本和交付稳定性 |

面板已经能展示真实状态，但确认与重试交互属于合成演示，真实模式继续只读。需求知识检索、持续一致性检查及错误自愈也尚非当前可用能力。[面板边界](local-panel.md)、[现有范围与检查依据](zoowork-improvement-backlog.md)

## 五 学习与改进的优先顺序

| 阶段 | 重点工作 | 希望形成的结果 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| P0 交付可信 | 需求行为验收、独立 CI、当前版本真实链路及失败恢复验收 | 一次交付能够证明需求行为、检查版本和实际发布对应 | 一条真实成功链路与关键失败场景有可复查证据 |
| P1 交付可复查和可复用 | 统一交付记录、阶段事件、审查摘要、角色 SOP、质量与成本指标 | 更容易审查、定位失败、恢复任务和复用方法 | 能从单条记录追溯需求到结果，并比较同类任务 |
| P2 场景扩展 | 单机运维保障、第二仓库试点，按需评估运行时替换和只读知识索引 | 验证可迁移性、运维责任和适配成本 | 真实需求触发，且有明确的权限、恢复和验收契约 |

上述次序的取舍是：**先降低错误交付风险，再减少重复人工工作，最后扩大平台覆盖面。** 运维保障若涉及长期无人值守或迁移，应提前成为前置工作。具体十二项工作与依赖沿用[已整理的改进清单](zoowork-improvement-backlog.md)，不重复建立另一套待办。

## 六 如何衡量学习是否有效

建议从少量真实任务开始保留以下指标，同时记录任务数量、需求版本与验收标准：

- 交付质量：验收通过数与总数、首次通过情况、用户发现的遗漏。
- 人工负担：实际审查与处理时间、介入次数，与等待时间分别统计。
- 恢复能力：失败阶段、恢复耗时、重试次数，以及是否重复产生外部产物。
- 总消耗：包含失败和重试的模型用量及其他成本；缺失数据记未知，估算与账单分开。
- 迁移成本：第二仓库所需的配置、适配和额外人工工作。

没有固定任务、相同标准和真实记录之前，不承诺效率提升比例或成本下降幅度。评价重点放在有效交付，而非模型调用次数、测试总数或演示步骤数量。

## 七 需要把握的边界

ZooWork 的优势判断主要基于公开产品设计和接口契约，本报告没有独立验证其实际稳定性、隔离强度、合规认证或客户收益。官网行业提效数字属于示意与基准场景，不用于本项目的收益预测。[官网说明](https://zoowork.ai/zh)

其公共 API 标注为 Developer Preview；开发文档也说明通用结果标签、数据集准备与后训练仍由应用负责。持续优化是值得借鉴的方向，不能理解成现成的全自动学习能力。[API 架构与状态](https://zoowork.ai/docs/zh/get-started/architecture)、[结果与训练边界](https://zoowork.ai/docs/zh/get-started/trajectories)

当前继续暂缓通用 Agent Builder、拖拽流程编辑器、插件市场、多租户、多 Agent 并发、自动训练、Triage 与错误自愈。后续如果引入第三方运行时，需求权威、审批和 Git／发布权限继续由 Spec Loop 控制器掌握。

本轮完成报告和建议整理，尚未启动开发。后续实施按已有工作方式拆分任务、独立评审和验证；每次真实业务 Merge 仍由用户显式确认。
