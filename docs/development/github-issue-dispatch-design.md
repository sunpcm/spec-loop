# GitHub Issue 排期与 Code Agent 派工设计

**V1 · 2026-11-21 · 首版接入计数器 `REQ-CNT-01`。** 文档 PR 合并后，需求生效，任务进入「待排期」。操作者在 GitHub Issue 上标记当前版本「可开工」后，调度器才有权启动 Code Agent。每个需求沿用一张主 Issue，每次派工都能追回当时的规格、任务和许可。

计数器的产品行为由已合入 `origin/main` 的需求文档定义。控制器为每个已确认版本冻结任务，生成 Issue 上的执行清单，并在领取作业时把同一份任务交给 Worker。[现行规格](../specs/counter.md) · [Planner](../../orchestrator/planner.ts) · [调度循环](../../orchestrator/runtime.ts) · [Worker](../../orchestrator/worker.ts)

GitHub Spec Kit 将规格、计划、任务和实施拆成可逐步审查的步骤。OpenHands 的 GitHub 集成允许操作者在 Issue 添加标签来触发编码，并在 Issue 中回报 PR。计数器借鉴这两个做法，并给每次确认后的任务分配独立开工标签，使操作者可以按版本排期。[GitHub Spec Kit](https://github.com/github/spec-kit#spec-driven-development) · [OpenHands 的 Issue 流程](https://docs.openhands.dev/openhands/usage/cloud/github-installation#working-with-issues)

## 1. 用计数器走一遍

飞书收到“给计数器加一个翻倍按钮，翻倍后还要能按原来的步长增加”。历史上，这项变更经过文档 PR #7、主 Issue #2 和代码 PR #8。下表沿用这三个记录说明新设计，`r1` 和开工标签是演练用的版本。[文档 PR #7](https://github.com/sunpcm/spec-loop/pull/7) · [主 Issue #2](https://github.com/sunpcm/spec-loop/issues/2) · [代码 PR #8](https://github.com/sunpcm/spec-loop/pull/8)

| 你会看到什么 | 系统做什么 | 谁决定下一步 |
| --- | --- | --- |
| 文档 PR 写明“3 翻倍得到 6，步长 2 保留” | 文档 Agent 草拟现有需求块，控制器校验后创建 docs-only PR | **你确认需求并合并文档 PR** |
| Issue #2 显示「待排期」，附本次目标、拆解和验收项 | 任务 Agent 提议计划，控制器保存 r1 并更新 Issue。队列空闲时也可以一直等待 | **你选择开工时机，在这张 Issue 添加 `可开工/r1`** |
| Issue 显示「可开工」或具体等待原因，例如“上一作业运行中” | 控制器核实打标人、版本、依赖、空闲名额，再领取一次作业。Worker 收到与 Issue 对应的任务 | 调度器自动派工 |
| 代码 PR 列出改动、对应需求版本和候选构建的验收结果 | 控制器运行类型检查、测试、构建和独立浏览器验收，通过后创建代码 PR | **你审查证据并确认合并代码 PR** |
| Issue 收到本地预览的部署版本与回执 | 控制器重新验收合并构建，健康检查通过后切换预览，再记录「已部署」 | 控制器完成交付 |

V1 的排期动作只有添加或在领取前撤下本版开工标签。操作者可以先确认多项需求，按希望的顺序放行。若多个任务同时可领，按有效许可的 GitHub 事件时间先后选择，时间相同按 Issue 编号排序。全局仍只有一个 Pi 作业。

## 2. 需求文档模板

文档 Agent 在固定主线快照上起草，向控制器返回 `{summary, content}`。首版入口只允许更新 `docs/specs/counter.md` 中现有的 `REQ-CNT-01`。下面的模板用于组织需求块。实际交付整份候选文档时保留已有行为、验收和块外内容。[飞书入口契约](feishu-intake-plan.md) · [需求块解析](../../orchestrator/specs.ts)

```markdown
### [<既有需求 ID>] <用户熟悉的功能名称>

#### 功能
- <用户在什么条件下执行什么动作，会看到什么结果>
- <这个动作涉及哪些已有行为或边界>

#### 验收
- <给定初始状态，执行动作，观察可判定的结果>
- <给定关联操作，验证前一个动作之后仍能得到预期结果>
```

**计数器写法。** 在既有块中增加“点击翻倍将当前计数乘以 2”。验收覆盖两件事。其一，当前值 3、步长 2，翻倍显示 6，随后点增加显示 8。其二，翻倍后重置显示 0，步长仍为 2。负责人、开工日期、任务勾选进度写在 Issue 中。现有解析器会对整个需求块计算哈希，在块内调整这些进度也会触发一次规格变更。

## 3. GitHub Issue 模板

每个 `repo + reqId` 复用一张受管主 Issue。下列模板为控制器维护的正文区段，每版发布时另留一条含版本、差异和操作键的评论。人的讨论、手记和排期说明放在评论或正文区段之外。任务拆到一次可验收、可交付的结果，本例的运算和按钮共用一个 Worker、一个代码 PR。

```markdown
标题：[<REQ-ID>] <功能名称>

### 本次交付 · <任务版本>
<一句话说明这次要交付什么>
依据：<固定提交上的规格链接> · <需求 ID> · <规格哈希短码>
状态：<待排期／可开工／编码中／待审代码 PR／交付结果>
下一步：<谁做什么，或正在等什么>

### 执行与验收
- [ ] <工作项> → <验收项引用>
- [ ] <工作项> → <验收项引用>
- 独立验收：<输入、动作、期望结果>
- 允许写入：<路径范围>。前置依赖：<已登记的依赖或“无”>。

### 交付记录
文档 PR <链接> · 代码 PR <生成后补> · 验收与部署回执 <产生后补>
```

**Issue #2 的 r1 样例**

| 字段 | 卡片上显示的内容 |
| --- | --- |
| 标题与目标 | `[REQ-CNT-01] 计数器与自定义步长`。本次交付翻倍按钮，点击后保留步长 |
| 依据与下一步 | 文档 PR #7，规格 `cb239039`。待排期，由操作者选择 `可开工/r1` |
| 编码清单 | 实现当前数值乘 2（A1）。将按钮接入页面，保留原步长及重置行为（A1、A2） |
| 独立验收 | A1 验证 `3 → 翻倍 6 → 增加 8`。A2 验证翻倍后重置为 0、步长仍为 2 |
| 范围、依赖与证据 | Worker 只写 `src/**`，前置依赖为空。验收证据关联候选版本，部署回执关联实际切换的版本 |

## 4. 任务 Agent 如何交给 Code Agent

任务 Agent 读取控制器提供的已确认规格和与上一版的差异，只提出目标、步骤和验收引用。控制器从 Git 确定来源、从仓库策略确定写入范围、为已登记的 Issue 分配任务版本。人读的 Issue 和 Worker 输入均从这一份已校验、冻结的任务记录生成。

以下是 r1 的交接示例。主线 SHA 和规格哈希取自 PR #7 合并时的真实快照。旧文档没有验收编号，控制器在本版内给原文分配 A1、A2。重新取得快照时可以按哈希和原文核对引用。

```json
{
  "schema": 1,
  "repo": "sunpcm/spec-loop",
  "issueNumber": 2,
  "revision": "r1",
  "reqId": "REQ-CNT-01",
  "specPath": "docs/specs/counter.md",
  "sourceMainSha": "b72a796f53cfad9769e8abfb612e30abed045a25",
  "specHash": "cb239039ca5ba35e151624c7a56272e5b1194aed2e0ceca8ad28a1b79f877060",
  "goal": "点击翻倍将当前计数乘以 2，保留步长",
  "steps": [
    {"text": "实现当前数值乘以 2", "acceptanceRefs": ["A1"]},
    {"text": "将翻倍按钮接入页面，保留步长与重置行为", "acceptanceRefs": ["A1", "A2"]}
  ],
  "acceptance": {
    "A1": "当前值为 3 时点击“翻倍”显示 6；翻倍不改变步长输入，之后仍可按原步长增加或减少。",
    "A2": "翻倍后再点击“重置”显示 0，步长保持不变。"
  },
  "allowedPaths": ["src/**"],
  "dependsOn": []
}
```

- **登记。** 控制器校验结构、长度、非空步骤、全部验收引用和边界。每项本次变更有可核对的规格依据。依赖由控制器解析到受管任务及已验证的完成结果。遇到未知依赖、循环、遗漏验收或冲突，Issue 显示具体原因。Planner 不可用时，仅当从规格能生成通过同样校验的最小任务才使用回退。重试登记优先复用已冻结记录。
- **交接。** Worker 收到冻结任务、同版本完整需求块和固定提交的源码快照。允许路径取自控制器策略，验收引用取自确认的文档。编辑 Issue、评论或勾选清单只会改变人看到的内容。受管字段被改写时，控制器提示差异并从冻结记录恢复。需要改变产品行为时回到文档 PR。Worker 只返回允许的源码变更。控制器执行 Git、GitHub、验收与发布操作，独立测试作者维护浏览器契约及预期哈希。
- **留证。** 作业、PR、验收与回执都带仓库、Issue、任务版本、规格哈希和来源 SHA。模型重试使用原任务。工作范围、验收、依赖或执行基线需要实质调整时，由控制器发布新任务版本并重新排期。勾选进度、历史链接和等待原因可以单独更新。

## 5. 标记「可开工」后的派工规则

### 版本与许可

本地状态为每张 Issue 持久保存单调递增的 `rN` 和历版任务。已使用或预留的编号永久占用，即使规格内容改回旧文本也分配新号。许可精确绑定受管仓库 ID、Issue 编号、`rN`、规格哈希和来源 SHA。Issue 的「下一步」只提示本版标签。GitHub 标签定义由整个仓库共享，清理旧标记时只从该 Issue 摘除。控制器可以创建标签定义，贴开工标签的动作由操作者完成。

1. **发布可排期的版本。** 首次建单先按仓库和需求 ID 保存创建意图，找回或创建主 Issue 并回填编号，再冻结带本版编号的任务。已有卡直接分配下一版本。更新受管区，发布版本评论，回读后保存评论 ID 和 GitHub 时间。卡片与冻结任务匹配后开放领取。各次远端写入结果未知时按各自操作键查询，补齐已有记录。
2. **识别操作者。** 轮询受管 Issue 的当前标签以及分页的 `labeled`、`unlabeled` 事件，按远端事件 ID 去重。只接受本版公布以后、来自配置中 GitHub 数字用户 ID 的有效添加事件。最新一次实际移除使尚未领取的许可失效，之后需要新的白名单添加事件。核对最新标签和事件次序后，在本地保存事件 ID、操作者 ID、许可时间与版本。事件缺页、先后无法证明、远端读取失败，或标签与事件不一致时暂停领取并显示原因。若同秒事件无法定序，提示操作者移除后重新添加。控制器与其他自动化使用独立账号时，打标记录也能区分人和程序。[GitHub Issue 事件接口](https://docs.github.com/en/rest/issues/events#list-issue-events) · [打标与撤标事件字段](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#labeled)
3. **选择可领取的任务。** 每轮先对账主线变更，再读许可。领取需要受管 Issue 已打开、本版规格和任务有效、依赖已完成、同一需求无活动交付且全局 Pi 名额空闲。缺许可显示「待排期」，有许可但名额或依赖未满足则显示具体原因。领取前刷新远端许可与主线，要求冻结提交仍在主线历史中，并确认该块的路径、哈希和版本。无关主线提交可以正常前进。
4. **先领取再启动。** 在现有单实例锁和串行状态更新内复核条件，为 `仓库 ID + Issue + rN + attempt` 唯一登记作业与许可事件，再启动 Worker。首次领取使用 attempt 1。重复轮询和打标只返回原作业。领取后撤标不会中断已启动的作业，之后另起 attempt 须有当版有效许可。候选分支、PR 查重键、验收与部署回执均包含任务版本，即使两版使用相同的规格哈希和源码 SHA，也能分别对账。
5. **恢复已领取作业。** 重启先核对作业、分支、PR 和回执。有可信记录证明尚未启动时接续原作业。启动结果不明时标为「待核实」，保留证据，暂停自动再调 Pi。明确失败后，既有显式重试才能增加 attempt，单独重贴标签不能重跑已失败的作业。部署失败只恢复部署，回执发送失败只补回执。已有源码满足需求时沿用 `satisfied` 回执，记录该版本的验收结果与“无需代码变更”。

控制器在验证、提交、推送、创建 PR、受控合并以及切换预览前再次核对版本。GitHub 写入和本地状态落盘分别完成。若新版生效恰逢旧请求已发出，按旧版操作键查明结果并关闭过期 PR。任何更新当前 Issue 状态的回调都要重新匹配当前任务版本。

## 6. 排期后需求又改了

例如 r1 已确认“翻倍保留步长”，随后业务提出“翻倍后把步长改为 1”。文档 Agent 先给出新文档 PR。**草案阶段仍以已确认的 r1 为准**，若想暂停尚未领取的 r1，操作者可以先撤下它的开工标签。新文档进入主线后，控制器在同一张 Issue 显示 r2、新旧验收差异和「待排期」。旧任务、旧许可和旧证据保留在 r1 的历史记录。

| r2 生效时 r1 到了哪一步 | 控制器怎样处理 | 操作者会看到什么 |
| --- | --- | --- |
| 待排期，或已许可、尚未领取 | 先把 r1 标过期并撤销本地许可，再同步卡片、清理过期标签。迟到的 r1 事件只记历史 | 同一 Issue 上的新验收条款与 `可开工/r2` |
| 已领取或正在编码、验证 | 尽力取消旧作业，保留现场。在产生外部效果前重新核验版本，拦截旧结果。旧作业退出或被确认停止后释放名额 | r1 标「已过期」。r2 可单独排期，若旧作业未退出则显示等待 |
| 代码 PR 已开、尚未合并 | 标记并关闭旧 PR，清楚写明替代版本。受控合并预检及最终确认均重查版本与 PR head | 历史 PR 链接、过期原因、新版待排期 |
| 旧 PR 已被人工合并，尚未切换预览 | 在切换和记账前拦截过期交付，保留原稳定预览。主线上已有的代码单独记录，交由新版验收或人工修正 | “r1 已合并、交付已过期”，新版继续待排期 |
| r1 已部署 | 保留 r1 的部署 SHA、健康回执及已发布事实。r2 通过自己的验收与部署后再切换 | “当前预览 r1，已确认需求 r2”，各有独立记录 |

控制器从持久游标沿 `main` 的第一父链顺序核对需求，追平本轮捕获的主线后才派工。离线期间即使内容经历“A → B → A”，原许可也作废。明确改用其他源码 SHA 重试时创建新版本。需求删除时终止尚未完成的交付并关闭受管卡。若旧 PR 的 `Closes #2` 已自动关闭新版任务，对账确认关闭来源后重新打开同一张卡，恢复新版的待排期状态。遇到人工关单或原因未知时展示原因并暂停领取。

主线历史、任务版本或远端 PR 状态无法核实时，显示「等待对账」。从旧备份恢复还须用远端版本评论、作业和 PR 找回已使用的最高版本号及相应关系。无法证明编号可安全续用时停在待核实。

## 7. 接入现有控制器与验收

| 改动位置 | 第一版的实现要求 |
| --- | --- |
| Planner、对账与状态存储 | 保存冻结任务、历版编号、发布记录、许可和领取记录。更新 Issue 时保留人工区。先对账规格再处理标签事件。[Planner](../../orchestrator/planner.ts) · [对账](../../orchestrator/reconciler.ts) · [状态存储](../../orchestrator/state.ts) |
| GitHub 适配与调度 | 增加带操作者的分页事件读取。在常规轮询、显式重试及基线恢复共用的 Worker 入口校验许可与版本。区分“恢复准备就绪”和“用户允许开工”。[GitHub 客户端](../../orchestrator/github.ts) · [调度循环](../../orchestrator/runtime.ts) · [重试基线](../../orchestrator/retry-baseline.ts) |
| Worker、合并、部署 | Worker 使用冻结任务。版本一路带到 PR、受控合并、预览切换及回执。旧回执按自身版本归档。[Worker](../../orchestrator/worker.ts) · [受控合并](../../orchestrator/merge.ts) · [部署](../../orchestrator/deploy.ts) |
| 切换已有数据 | 在单一控制器暂停领取时迁移。无版本许可的旧 `todo` 进入待排期。盘点既有活动作业、开放 PR、部署和待补回执，按证据接续或转人工核实。已部署记录保留，存量 Issue 不重复创建。备份状态后迁移，遇到不识别的状态版本停止领取 |

**第一版通过条件**

| 场景 | 可观测结果 |
| --- | --- |
| 合并文档，空闲时连续轮询三轮 | 一张主 Issue、一份当前任务、零次 Code Agent 调用。重启、手改正文、勾选清单或旧的 `status:todo` 均不能开工 |
| 白名单用户打本版标签，首次领取前有其他任务占用名额 | 先显示等待。名额释放后只领取一次，Worker 输入和 Issue 引用同一版任务，重复轮询及打标不会产生第二个作业 |
| 非白名单账号打标，或合法打标后在领取前撤标 | 均保持零次派工。之后有效的当版授权可正常领取 |
| r1 获准后 r2 生效，随后收到 r1 的标签事件、重试或迟到的成功回调 | r2 保持待排期。r1 结果只进入历史，不能生成当前 PR、切换预览或覆盖 r2 状态 |
| 排队期间只合入无关文件，或控制器离线时规格经历 A → B → A | 前者可按原冻结提交开工。后者须对新版本重新打标，原许可和 PR 均不能复用 |
| 登记或创建 PR 超时，或控制器在领取与调用之间退出 | 已有 Issue、分支、PR 和作业按操作键找回。启动结果未知显示待核实。补写标签或回执不会新增 Worker 调用 |
| 用户确认代码 PR，合并构建或健康检查失败 | 保留旧预览，Issue 显示失败及恢复动作。恢复部署成功后写同版本回执并标记已部署 |

实施时先用临时仓库、模拟 GitHub 和 Pi 验证上述场景，再用固定类型检查、测试、构建及独立浏览器门禁验证交付。真实验收须留存一次从文档确认、待排期、人工打标到代码审查和部署回执的记录，并验证一次排期后改版导致旧许可失效。
