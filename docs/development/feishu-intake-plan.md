# 飞书需求入口实施计划

日期：2026-11-14。适用基线：`main` 406d27b。

## 1. 目标与启用方式

本增量把飞书从“看通知、查状态”扩展为结构化需求入口。新入口启用需合并本 PR 并重启控制器；启用后，每次业务需求保留两次确认合并。受管 PR 可使用后续新增的受控飞书入口，契约见 [飞书受控确认合并 PR](feishu-merge-plan.md)。

1. 白名单操作者向唯一绑定会话发送 `需求：描述` 或 `/require 描述`。
2. `spec-author` 只生成 `docs/specs/counter.md` 的候选内容，控制器创建 docs-only PR 并添加 `spec-patch` 标签。
3. 用户确认合并文档 PR；文档进入 `main` 后自动触发现有编码闭环，产生只修改 `src/**` 的代码 PR。
4. 用户确认合并代码 PR 后，现有部署流程构建并切换本地预览。

首版只修改现有 `REQ-CNT-01`，不做普通闲聊、多轮澄清、多轮编辑、新增或删除需求块、写入其他文档或仓库、自动 Merge（受控二次确认入口除外）、Triage 与错误自愈。

## 2. 用户契约

### 2.1 需求命令

只接受文本消息，且必须满足下列之一：

```text
需求：在计数器页面增加“翻倍”按钮，点击后把当前值乘以 2。
```

```text
/require 在计数器页面增加“翻倍”按钮，点击后把当前值乘以 2。
```

- 中文或 ASCII 冒号均可；冒号后的首尾空白会被规范化。
- 描述保留内部换行，长度为 1～2000 字符。
- 仅支持文本消息；非文本消息不进入需求处理，首版不承诺自动回复。
- 空描述、只有空白或超过 2000 字符时返回中文错误，不调用 Pi。
- 请求 ID 为 12 位小写十六进制，例如 `a1b2c3d4e5f6`。
- 同一飞书 `messageId` 的重复投递必须复用持久记录，不能再次调用 Pi 或重复创建 PR。
- 同一 `counter.md` 目标只能有一个未结束需求或文档 PR。重复描述复用现有请求；其他新描述返回当前请求 ID、阶段和 PR 链接，提示先完成现有交付。
- 已有活动 Worker 或代码 PR 时，新需求同样被拒绝，避免并行交付争用同一需求。

### 2.2 状态、重试与帮助

- `状态` 返回需求请求 ID、当前阶段、文档 PR/代码 PR，或脱敏后的错误摘要。
- `重试需求 <请求ID>` 只恢复该需求请求，不与原有 `重试 #<Issue编号>` 混用；两者分别操作 spec 请求和编码 Issue。
- `帮助` 与 `/help` 返回中文命令说明，强调“先合并文档 PR，再合并代码 PR”。
- 未知文本返回同一帮助，不进入需求、闲聊或编辑流程。
- 通知失败不回滚已创建的 commit/PR；再次发送 `状态` 或 `重试需求` 应能重新取得链接。

### 2.3 手机操作

手机飞书承担提交、观察、打开 GitHub 链接，以及在受控合并入口启用后预检和确认受管 PR；未启用或不符合受管条件时，Merge 仍由用户在 GitHub 页面完成。

```text
需求：在计数器页面增加“翻倍”按钮，点击后把当前值乘以 2。
```

收到“已接收 + 请求 ID”后发送：

```text
状态
```

文档 PR 通知到达后人工 Merge；代码 PR 通知到达后再人工 Merge。若通知显示可恢复失败，使用其中的请求 ID：

```text
重试需求 a1b2c3d4e5f6
```

## 3. 实施步骤

### 第一步：命令入口与队列

- 在飞书事件入口识别 `需求：`、`/require `、`状态`、`重试需求`、`帮助` 与未知文本。
- 先通过现有绑定会话与操作者白名单，再解析和校验长度；所有有效需求进入与 Planner、Worker、轮询共用的全局串行队列。
- 快速 ACK 只表示消息已接收，不代表 Pi、PR 或 Merge 成功。

完成条件：命令测试覆盖中文/ASCII 冒号、换行、1/2000 字符边界、空与超长输入、未知反馈、会话和操作者拒绝。

### 第二步：`spec-author` 与文档校验

- 固定读取 `origin/main:docs/specs/counter.md`，连同用户文本交给 `spec-author`。
- `spec-author` 使用现有无工具 Pi 沙箱、环境白名单、5 分钟超时和作业内 `agentDir`；不得获得 GitHub 凭据、shell 或仓库写权限。
- 模型只返回 `{summary, content}` JSON；控制器限制输出大小并验证 JSON 结构、目标路径、完整 Markdown 内容、需求 ID/块保留、格式合法和内容确有变化。
- 模型输出与飞书文本只作为数据，拼接 shell 命令时不得插值。

完成条件：无效 JSON、额外字段或路径、越权 Markdown、删除/新增需求块、未变化内容、超时和过大输出均被拒绝且状态可见。

### 第三步：docs-only commit 与 PR

- 控制器在受控 `runDir` 写入唯一白名单文件，提交到确定性分支 `pi/spec-<请求ID>`；提交前再次 fetch 并检查当前主线仍等于请求 `baseSHA`。
- 检查 commit 只包含 `docs/specs/counter.md`，目标文件无符号链接或越权路径；创建带 `spec-patch` 标签的 PR。
- PR 正文记录 `kind=spec-request`、请求 ID、源 `main` SHA 和来源摘要，不使用 `Closes`。
- 文档 PR 只能作为用户确认合并的候选，不能直接创建业务 Issue、修改 `src/**`、推进需求游标或更新生产预览。

完成条件：PR diff、标签、正文元数据和分支可重复对账；push、PR 或加标签失败后只恢复后续阶段。

### 第四步：持久状态、两段交付与恢复

- 状态 schema 1 新增可选 `specRequests`，旧状态在没有该字段时仍可加载；保存消息 ID、稳定请求 ID、描述、`baseSHA`、分支、阶段、commit、PR、错误和时间。
- 所有状态更新通过 `StateStore` 串行落盘；阶段先落盘再产生外部效果。
- `runOnce` 和显式重试先做无 Pi 的远端对账。查找 PR 时包含 all 状态；远端读取失败当作未知并 fail closed，不能把它当作不存在。`status` 只读取本地 `StateStore` 快照，Pi 执行期间也能立即返回当前阶段。
- 已生成有效文档、commit、push、PR 或标签的请求，重试只恢复未完成阶段；已合并或已关闭 PR 不重新创建。
- 文档 PR 合入后由现有“文档到代码 PR、人工确认合并到部署”链路接管；代码 PR 仍由用户确认合并。

完成条件：消息重投和进程重启不重复调用 Pi/建 PR；单目标冲突、`main` 漂移、创建结果不明、push/PR/label 故障和分阶段恢复均有确定性结果。

## 4. 验收矩阵

| 场景 | 通过条件 |
| --- | --- |
| 有效需求 | 立即 ACK，返回稳定请求 ID，保留内部换行，全局串行执行 |
| 无效输入 | 空、超长或未知文本返回中文反馈，不调用 Pi |
| 非文本消息 | 仅支持文本；非文本消息不进入需求处理，不承诺自动回复 |
| 文档生成 | 只改 `counter.md` 的现有 `REQ-CNT-01`，无新增/删除其他需求块 |
| 文档 PR | 分支、commit、标签、PR 元数据和 diff 全部符合契约，无 `Closes` |
| 幂等 | 同一 `messageId` 重投、同描述冲突和进程重启均不重复调用 Pi/建 PR |
| 并发 | 同一目标已有未结束 spec/代码交付时，新请求被拒绝并返回现有链接 |
| 主线漂移 | 当前 `main` 不等于请求 `baseSHA` 时停止生成或发布旧文档 |
| 远端故障 | 远端状态不明时 fail closed；已创建 PR 不因通知或本地持久化故障丢失 |
| 阶段恢复 | 显式 `重试需求` 只恢复失败阶段，不重复已有有效产物 |
| 业务人工卡点 | 业务文档 PR 与代码 PR 都需要用户确认合并；Agent 不未经确认自主 Merge |
| 真实联调 | 白名单绑定会话、真实 Pi、真实 GitHub PR 与部署链路均产生可核验证据 |

单元与夹具测试由代码节点负责；文档节点只检查链接、Markdown 格式和事实一致性。

## 5. 风险与边界

- **单目标锁**：首版只为 `counter.md` 的 `REQ-CNT-01` 建锁，不代表通用多文档并发能力。
- **业务两段 Merge**：业务文档 PR Merge 后才触发代码生成，代码 PR Merge 后才部署。关闭 Issue 或出现 Vercel Preview 都不等于发布完成。
- **主线漂移**：旧请求固定 `baseSHA`，漂移后要求重新提交需求；不对新 main 上的旧文档做盲目重放。
- **未知远端状态**：GitHub 读取失败时停止恢复，避免在不确定状态下重复创建分支、commit 或 PR。
- **模型边界**：`spec-author` 只能返回候选文档 JSON；结构和内容验证失败即失败，不把模型原始输出直接写入仓库或发给飞书。
- **通知解耦**：飞书发送失败不阻断 GitHub 主链路，也不回滚已创建对象。
- **暂缓能力**：普通闲聊、自然语言澄清、多轮编辑、多需求块、其他文件/仓库、自动 Merge（受控二次确认入口除外）、Triage 与错误自愈不在首版范围。
- **验收边界**：云上 Vercel Ready 不能替代本地控制器验收。

## 6. 验收要求与证据

- 代码节点交付源码与测试；独立节点按固定主线、需求版本、权限边界、恢复路径和历史 PR 回归完成 Review。
- 主 Agent 独立执行类型检查、全量测试、构建和关键恢复路径验收，并核对实际命令、退出码与失败摘要。
- 真实飞书消息、真实 Pi、真实 GitHub PR 及后续部署链路必须留下可核验证据；模拟测试不能替代真实联调。
- 用户完成文档 PR 与代码 PR 两次确认合并，且部署链路完成后，才认定业务链路交付完成。
- 每轮实施和评审的命令、退出码、失败、未验项与冻结状态记录在 `.review/reports/`；文档只保留长期有效的验收要求。
- Vercel Ready 只代表静态前端云端部署，不能替代本地控制器、Pi 与飞书入口验收。

更多配置、恢复命令和验收记录见 [飞书配置](feishu-setup.md) 与 [第一轮启动与验收指南](demo-runbook.md)。
