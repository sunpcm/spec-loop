# 飞书 Demo 开发计划

日期：2026-11-14。状态：计划已整理，尚未开始编码。

## 1. 本轮目标

先做一个能够现场演示的本地系统：**飞书看进度 → 修改需求生成代码 PR → GitHub 人工 Merge → 本地页面更新 → 页面报错推动修复。**

固定选择：GitHub 仓库 `sunpcm/spec-loop`；飞书企业自建应用机器人，长连接接收消息；Node.js/TypeScript 编排器；Vite + 原生 TypeScript 计数器页面；Planner、Worker、Triage 使用无头 Pi。

本计划作为当前 Demo 的范围与开发顺序入口。原需求、架构与实施文档保留为参考，原评审报告保留为后续风险清单；不再要求先完成全部通用恢复设计才做 Demo。产品行为仍以 `docs/specs/*.md` 为准，人工 Merge 与角色写入边界继续保留。

## 2. 首版范围

| 包含 | Demo 的具体做法 |
| --- | --- |
| 仓库与用户 | 一个仓库、一个操作者、一个飞书会话 |
| 前端 | 一个计数器，合法输入正常工作，空步长可稳定触发演示错误 |
| 需求入口 | 人工编辑文档，commit 并 push 到 main；后台监听远端主线 |
| 开发 | 一个需求块对应一个主 Issue，Agent 编码、检查并提代码 PR |
| 报错自愈 | 文档缺边界则提文档 PR；代码违约则建修复 Issue；均回到 Worker |
| 发布 | 用户在 GitHub Merge，后台构建并切换本地预览 |
| 飞书 | 阶段通知、Issue/PR 链接、`状态`、`重试 #N` |
| 并发 | 全局一个 Pi 作业；同一需求只维持一份活动代码交付 |

暂缓：IM 自然语言直接提需求、IM 内 Merge、多群多用户、多仓、多任务并行、云端部署、通用需求验收生成、任意历史回退及复杂崩溃恢复。失败先留痕并支持定向重试；无法安全恢复的场景明确提示人工处理。

## 3. 开发顺序

| 阶段 | 开发内容 | 完成判据 |
| --- | --- | --- |
| ① 基础跑起来 | 保留当前文档，初始化并关联指定 GitHub 仓库；建立 package/scripts、计数器需求与前端；验证 gh、Pi、模型及最小隔离 | 页面可打开；构建/关键行为检查通过；真实 Pi 能调用，越权写入探针被阻断 |
| ② 飞书接通 | 自建应用长连接；发送通知；接收白名单用户的 `状态` 命令；完成本地配置示例 | 飞书发“状态”得到本地服务回复，本地能向指定会话推送消息 |
| ③ 文档到代码 PR（A） | 主线需求解析、GitHub Labels/Issue、Planner、串行 Worker、src 路径限制、校验、提交/push/PR、飞书阶段通知 | 改“增加减少按钮”并 push 后，真实 Issue 和代码 PR 出现，飞书收到链接 |
| ④ Merge 到部署（C） | 轮询受管 PR；独立构建；更新稳定预览；部署回执与关单；飞书结果通知 | 人工 Merge 后页面出现减少按钮，显示正确部署版本，Issue 标 done |
| ⑤ 错误到修复（B） | HTTP 报错接收、基础去重、Triage 分类、docs-only PR 或修复 Issue、复用 A/C | 空步长报错触发文档补丁；人工 Merge 后自动生成代码修复 PR；再 Merge 后错误消失。另验证一次“文档已规定但实现违约”路径 |
| ⑥ 演示收口 | `重试 #N`、超时/失败通知、最小重启对账、一键启动、操作指南；集中复核 | 两个演示场景重复运行不重复建单；失败可见且重试目标正确；保留真实 GitHub/Pi/浏览器证据 |

**第一个可展示里程碑：完成①～④。** 此时已能演示“文档驱动开发 + 飞书通知 + 人工合并部署”。

**完整 Demo 里程碑：完成⑤～⑥。** 三个闭环均用真实 GitHub 和 Pi 跑通，不用模拟结果代替。

每个阶段先交付可运行结果与关键检查，再进入下一阶段；不先铺完整平台或全部抽象。收口时保留实施与独立评审分离，重点审查真实演示链路。

## 4. 飞书首版体验

通知只覆盖重要阶段，不把完整模型输出发到群里：

```text
📋 REQ-CNT-01 已创建任务 #12
🛠️ Worker 正在实现“增加减少按钮”
🔎 PR #13 等待审查：https://github.com/sunpcm/spec-loop/pull/13
🚀 已部署：<commit SHA>，预览 http://127.0.0.1:5173
⚠️ 收到计数器错误，正在判断文档缺失还是实现缺陷
📄 文档补丁 PR #14 等待人工确认
❌ 任务 #12 构建失败，可发送“重试 #12”
```

示例编号仅用于说明，不代表已创建远端对象。PR 使用普通可点击链接即可，首版不做复杂交互卡片。

- `状态`：返回当前任务、最近 PR、运行阶段和部署版本。
- `重试 #N`：只重试该受管任务的失败阶段；部署失败只重试部署。
- 没有 Issue 的失败显示 jobId 和本地恢复提示，不把未知作业当代码任务重跑。
- Merge 始终跳转 GitHub 人工操作。
- 本地预览 URL 仅对运行 Demo 的电脑有效；手机飞书能看通知和 GitHub 链接，不承诺能打开电脑回环地址。

## 5. Demo 仍需保留的最低保障

- **写入边界**：Planner 不写仓内文件，Worker 只写 src，Triage 只写指定 specs；控制器执行 git/gh，检查进程不继承 GitHub/模型凭据。
- **单实例与去重**：一个守护进程、一个 Pi 作业，状态变更串行写入；任务绑定需求变更提交和执行尝试，重启先与远端对账。
- **避免过期交付**：需求更新作废旧交付；已有同需求代码 PR 时，新错误先关联或排队，不再生成竞争 PR。
- **失败有出口**：Pi 默认 5 分钟超时，失败写本地日志并尽可能同步 Issue/飞书；飞书故障不使 GitHub 主链路失败，GitHub不可用时保留待同步状态。
- **完成有证据**：只处理经过人工 Merge 的代码；按计数器演示脚本验收实际预览后标 done；不启用自动 already-satisfied 关单。PR 的 Closes 自动关单不替代部署成功回执。
- **自愈有上限**：相同错误不重复开活动任务；同一错误自动修订最多两轮，证据不足或超出上限转人工。旧页面报错不直接当作已修复。

这些保障只实现支撑 Demo 的最小版本；多机器锁、完整事件框架、通用恢复引擎等后置。

## 6. 需要准备的环境

| 项目 | 当前状态 / 准备项 |
| --- | --- |
| GitHub | 仓库已创建；上次只读检查分支列表为空，本地尚未初始化/关联；开发时建立首次 main 基线并检查 gh 登录 |
| Pi | 上次 shell 未找到 pi；开发时安装并锁定版本，配置各角色可用模型，做真实冒烟 |
| 飞书应用 | 创建企业自建应用，开启机器人，配置长连接及接收消息事件、发送/接收所需最小权限，确保应用对操作者可用 |
| 飞书本地配置 | App ID、App Secret、目标会话 ID、允许操作者 ID；秘密只在本地配置，不进 Git 或飞书消息 |
| 本机网络 | 能访问 GitHub、飞书和选定模型服务；长连接接收消息无需公网回调地址 |

飞书可先建立单聊或专用演示群，首版只绑定其中一个。配置机器人本身和开发代码分开推进，避免最后才发现消息权限或应用可用范围未配置。

## 7. 最终现场演示

1. 启动本地服务，在飞书发送“状态”，确认版本和任务队列。
2. 修改计数器需求，定义减少按钮，commit/push。
3. 展示飞书阶段通知、GitHub Issue 和 Worker 代码 PR。
4. GitHub 人工 Merge，展示页面新增行为与部署成功通知。
5. 清空步长触发错误，展示 Triage 的文档补丁 PR。
6. 人工合并文档 PR，展示自动产生的代码修复 PR；再合并并验证空输入不再报错。
7. 用预先准备的受控回归验证“文档已规定 → 修复 Issue”，并展示一次失败/重试。

交付：可运行源码、环境配置示例、`demo:init`/`demo` 入口、演示指南，以及真实 Issue/PR/部署版本的记录。当前仅完成计划整理，不表示已完成任何开发阶段。
