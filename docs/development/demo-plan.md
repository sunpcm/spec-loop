# 飞书 Demo 开发计划

日期：2026-11-14。阶段①～④已真实完成；PR #1、#3、#4 均由用户人工 Merge，`main` 406d27b 已验收。Vercel 正式入口为 <https://spec-loop-three.vercel.app/>，当前需账号登录。当前增量是飞书结构化需求入口，阶段⑤错误自愈以及普通闲聊、多轮澄清编辑后置。

## 1. 本轮目标

先做一个能够现场演示的本地系统：**飞书看进度 → 修改需求生成代码 PR → GitHub 人工 Merge → 本地页面更新 → 页面报错推动修复。**

固定选择：GitHub 仓库 `sunpcm/spec-loop`；飞书企业自建应用机器人，长连接接收消息；Node.js/TypeScript 编排器；Vite + 原生 TypeScript 计数器页面；Planner、Worker、Triage 使用无头 Pi。

本计划作为当前 Demo 的范围与开发顺序入口。原需求、架构与实施文档保留为参考，原评审报告保留为后续风险清单；不再要求先完成全部通用恢复设计才做 Demo。产品行为仍以 `docs/specs/*.md` 为准，人工 Merge 与角色写入边界继续保留。

阶段 1～4 已证明“文档变更 → 代码 PR → 人工 Merge → 部署”的基础闭环。当前增量增加受控确认合并：合并入口启用需合并本 PR 并重启控制器；飞书结构化需求入口已由 PR #6 合并启用。之后每次业务需求由 `spec-author` 生成现有计数器文档候选，再依次完成业务文档 PR 和代码 PR 合并。具体契约见 [飞书需求入口实施计划](feishu-intake-plan.md) 和 [飞书受控确认合并 PR](feishu-merge-plan.md)。

## 2. 首版范围

| 飞书 | 需求提交快速 ACK、阶段通知、PR 链接、`状态`、`重试需求 <请求ID>`、帮助反馈 |
| 并发 | 全局一个 Pi 作业；同一 `counter.md` 目标只维持一个未结束请求/PR |

## 4. 飞书需求入口体验

入口启用后，白名单操作者在唯一绑定会话发送：

```text
需求：在计数器页面增加“翻倍”按钮，点击后把当前值乘以 2。
```

也兼容：

```text
/require 在计数器页面增加“翻倍”按钮，点击后把当前值乘以 2。
```

描述保留换行，限制 1～2000 字符；仅支持文本消息。通知只覆盖重要阶段，不发送完整模型输出、命令原始 stdout 或秘密：

```text
✅ 已收到需求消息，候选请求ID：a1b2c3d4e5f6；检查通过后受理
📄 文档 PR #20 等待人工 Merge：https://github.com/sunpcm/spec-loop/pull/20
人工 Merge 文档 PR 后自动编码，代码 PR 仍需人工 Merge
🔎 代码 PR #21 等待人工 Merge：https://github.com/sunpcm/spec-loop/pull/21
🚀 代码 PR 已 Merge，部署回执：<commit SHA>
❌ 需求 a1b2c3d4e5f6 在 create-pr 阶段失败，可发送“重试需求 a1b2c3d4e5f6”
```

示例编号仅用于说明，不代表已创建远端对象。PR 使用普通可点击链接即可，首版不做复杂交互卡片。

- `状态`：返回需求请求 ID、当前阶段、文档 PR/代码 PR；仓库任务仍可显示最近 Issue/PR 和部署版本。
- `重试需求 <请求ID>`：只恢复对应需求请求中未完成的阶段，已有效生成的文档/commit/PR 不重复创建。
- `重试 #N`：继续用于既有 Issue/Worker 交付，与需求请求重试相互独立。
- `帮助`、`/help` 或未知文本：返回中文帮助，未知文本不进入需求生成或闲聊。
- 没有 Issue 的失败显示 jobId 和本地恢复提示，不把未知作业当代码任务重跑。
- Merge 由绑定会话中的白名单用户显式确认；受管 PR 可在受控飞书入口完成，其他 PR 仍跳转 GitHub 人工操作。
- 本地预览 URL 仅对运行 Demo 的电脑有效；手机飞书能看通知和 GitHub 链接。Vercel 正式入口需账号登录。

## 5. Demo 仍需保留的最低保障

- **写入边界**：`spec-author` 只输出 `{summary, content}` 且只能映射到 `docs/specs/counter.md`；Planner 不写仓内文件，Worker 只写 `src/**`；控制器执行 git/gh，检查进程不继承 GitHub/模型凭据。
- **单实例与去重**：一个守护进程、一个 Pi 作业，状态变更串行写入；飞书 `messageId` 持久去重，同一目标只允许一个未结束请求/PR，重启先与远端对账。
- **两段业务 Merge**：每个业务需求的 docs-only PR 由用户确认合并后才触发编码，代码 PR 再由用户确认合并才部署；任何 Agent 不未经确认自主 Merge。
- **避免过期交付**：需求更新作废旧交付；已有同需求代码 PR 时，新错误先关联或排队，不再生成竞争 PR。
- **主线固定**：需求请求记录源 `baseSHA`；创建/发布前发现 `main` 漂移即停止，要求基于新主重新提需求。
- **失败有出口**：Pi 默认 5 分钟超时，失败写本地日志并尽可能同步 Issue/飞书；飞书故障不使 GitHub 主链路失败，GitHub不可用时保留待同步状态。
- **阶段恢复**：先落盘阶段再产生外部效果；push、PR、标签和通知失败后仅由显式重试恢复，远端读取失败时 fail closed。
- **完成有证据**：只处理经过人工 Merge 的代码；按计数器演示脚本验收实际预览后标 done；不启用自动 already-satisfied 关单。PR 的 Closes 自动关单不替代部署成功回执。

这些保障只覆盖单仓库、单操作者、单飞书会话和单 Pi 作业；多机器锁、完整事件框架、通用恢复引擎、Triage 和错误自愈仍后置。

## 7. 最终现场演示

入口启用后按以下步骤操作：

1. 启动本地服务，在飞书发送 `状态`，确认已验收版本和任务队列。
2. 发送 `需求：在计数器页面增加“翻倍”按钮...`，确认快速 ACK、请求 ID 和串行队列。
3. 展示 docs-only PR 只修改 `docs/specs/counter.md` 的现有 `REQ-CNT-01`，并带 `spec-patch` 标签。
4. 通过 GitHub 网页或受控飞书入口确认合并文档 PR，展示现有 A/C 自动产生代码 PR。
5. 通过 GitHub 网页或受控飞书入口确认合并代码 PR，展示部署回执和页面新增行为。
6. 重投同一消息和发送冲突需求，确认不重复调用 Pi/建 PR，并获得当前请求链接。
7. 演示一次可恢复失败，发送 `重试需求 <请求ID>`，确认只恢复未完成阶段。

具体命令与风险见 [飞书需求入口实施计划](feishu-intake-plan.md)，运行步骤见 [第一轮指南](demo-runbook.md)。
