# 飞书受控确认合并 PR（Demo）

本文描述本分支新增的飞书受控确认合并契约。该能力尚未在当前部署启用；必须先由用户人工合并本功能 PR，再重启控制器。启用前，既有 GitHub 网页人工 Merge 流程继续有效。

## 1. 启用条件与边界

- 启用前置条件：本功能 PR 先进入 `main`，控制器重启加载新代码和状态契约。重启前不能把本文中的命令当作可用能力。
- 首版只支持当前绑定仓库内 `headRepo` 与主仓相同的受管 `pi/spec-*` 文档 PR 或 `pi/req-*` 代码 PR，目标分支必须是 `main`。
- 不支持 fork、跨仓、草稿、冲突、被保护规则阻塞、检查失败、检查状态未知、非受管 PR 和非 `main` 目标。
- 模型、实施 Agent 和运行中的 Planner/Worker 都不得自主选择或发起 Merge。控制器只在收到绑定会话中白名单用户的显式确认后执行。
- 不使用 `--admin`、`--auto`、异步合并队列、删除分支或绕过 GitHub 分支保护。
- 命令不能通过控制 API/HTTP 触发。`状态` 仍是只读即时返回；`合并 PR #N`、`确认合并` 和既有需求任务共用全局串行队列。

## 2. 命令

| 命令 | 行为 |
| --- | --- |
| `合并 PR #N` | 只做预检，不写远端；返回 PR 信息、检查概要和确认码 |
| `/merge N` | `合并 PR #N` 的 ASCII 别名 |
| `确认合并 #N <8位hex确认码>` | 重新校验并执行同步 SHA 锁定 Merge |

确认码是 8 位十六进制随机值，10 分钟内有效。它绑定仓库、PR、headSHA、baseSHA、原始 `messageId`、规范化操作者 ID、绑定会话和阶段。过期、错号、错码、跨人、跨会话的确认码都拒绝。已发起或已合并的确认码不生成新许可，也不再发送 PUT；按持久记录只读回查，并幂等返回当前结果。

## 3. 身份与权限

- 只处理绑定飞书会话、白名单用户和真实 `sender_type=user` 的消息。
- 操作者、会话和 `messageId` 必须来自桥接传入的可信事件上下文，不得从用户文本解析身份。上下文缺失时拒绝。
- 重新使用现有飞书和 GitHub 配置；不新增公网入口。GitHub 凭据仍只归控制器使用，Pi 和本地验证进程不获得凭据。
- 本地审计只记录可信 actor、`messageId`、PR、headSHA、确认码处理结果和失败原因；不向远端发送个人标识或确认码。

## 4. 预检

预检会重新读取 PR 元数据、变更文件清单和该 PR 当前 head 上的检查。

预检通过时返回仓库、PR 标题/链接、受管类型、headSHA、目标 `main`、检查概要和确认命令。没有远端 checks 时明确显示“无远端检查”，但仍要求存在已有本地验证记录。

预检要求：

- PR 是 open、非 draft、`mergeable=true` 且 `mergeable_state=clean`。
- 文档 PR 的 PR、分支、commit SHA、baseSHA、已验证文档内容和请求状态互相一致；变更只允许 `docs/specs/counter.md`。
- 代码 PR 的 PR、job、jobId、attempt、specHash、sourceMainSha 和当前需求一致；当前 `origin/main` 的需求哈希仍匹配；headSHA 等于本地受管生成分支的提交；变更只允许 `src/**`。
- 拒绝重命名旧路径、symlink、非 `100644` 文件模式或越权路径。
- 远端变更清单必须完整读取；数量、分页或不确定性无法消除时 fail closed。
- 不把 PR 正文中的 ✅ 或其他字符串当作检查凭据。

## 5. 确认与执行

用户发送确认命令后，控制器先重新读取 PR、head、base、检查和确认记录。确认时再次核对所有绑定字段；主线或 base 漂移、head 更新作废确认码。检查未通过、pending、cancelled、failed、状态未知或读取失败时拒绝发送 PUT；确认记录仍有效时，可等待检查恢复后再次确认。

执行使用同步 API，并把已确认的完整 headSHA 锁进请求：

```bash
gh api --method PUT repos/sunpcm/spec-loop/pulls/<PR编号>/merge \
  -f sha=<已确认完整headSHA> \
  -f merge_method=merge
```

远端锁定边界：预检和确认都会复核 headSHA 与 baseSHA，但 GitHub Merge REST 只按请求中的 `sha` 原子锁定 PR head。base 在最终复核到服务端执行之间仍可能被外部更新，不存在 headSHA 加 baseSHA 的远端双原子锁。本轮单操作者 Demo 接受该窗口；控制器仍服从 GitHub 分支保护和合并校验，不得宣称双 SHA 远端原子锁定。

执行顺序如下：

1. 先把 `attempted` 阶段持久落盘。状态写失败时不发 PUT。
2. 调用同步 Merge API，并校验响应中的 `merged=true` 和 merge SHA。
3. 回读 PR，确认已合并且对应 head 一致。
4. 成功后落盘结果并交给既有 A/C 轮询。

旧交付兼容边界：受控代码 PR 必须存在可信验证记录，且记录中的 headSHA、受控本地 branchSHA 和真实 PR head 一致。缺少该记录的历史代码 PR 会被飞书合并拒绝；用户仍可走 GitHub 网页人工入口。这类旧交付不因拒绝 Merge 而改写或补发新的远端许可。

Merge 成功只表示 PR 进入 `main`，不表示编码或部署完成。控制器不得直接把任务标为 done 或关闭任务；后续文档对账、代码构建、健康检查和预览切换仍由现有 A/C 轮询接管。

## 6. 演示流程

启用后可用占位 PR 编号演示：

```text
状态
合并 PR #<PR编号>
确认合并 #<PR编号> <确认码>
状态
```

预检返回后，先核对 PR 链接、headSHA 和检查概要，再发送确认。确认成功后的中文回复是“已合并，后续编码/部署处理中”。不要把它解读为部署完成；继续用 `状态` 和本地预览等待既有部署链路。

## 7. 失败与恢复

- 预检或确认拒绝时只返回失败原因和 PR 网页链接；不写远端。
- 显式 API 失败时要求重新预检和重新确认。
- API 超时或结果未知时，控制器先回读 PR；结果未知时持久记录 `unknown/attempted`，只允许读对账，不盲目重发 PUT。
- 相同 `messageId` 或相同确认码重放不生成新许可、不重复 Merge；已合并 PR 返回幂等结果，关闭但未合并的 PR 拒绝。
- 成功后状态写失败或控制器重启时，凭 `attempted` 加远端对账恢复结果，不重复 PUT。
- 重启保留确认码 TTL 和已有处理结果。从未发起确认的 confirmable 记录在 TTL 过期后必须重新预检；已进入 attempted/unknown 的记录即使超过 TTL，也只读远端对账恢复，不生成新许可。
- 飞书通知失败不改变 Merge 结果；用 `状态` 查询后续阶段。合并后的部署失败按原有 A/C 恢复路径处理。

## 8. 状态与日志

- `状态` 可显示最近合并阶段，但不改变任务语义。
- `帮助` 和 `/help` 包含两条新命令。本文明确：“已合并”不等于部署完成。
- `[MERGE]` 日志必须脱敏，GitHub 错误摘要保持有界；secret、确认码和个人标识不进入远端回执。

## 9. 当前验收边界

本文只描述待启用契约，不代表已上线或已真实验收。测试必须使用临时 Git 仓库、模拟 gh、模拟飞书和受控 fixture，不做真实远端 Merge。真实启用前由主 Agent 独立检查，并由用户人工合并本功能 PR 后重启控制器。
